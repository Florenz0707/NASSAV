# 通知时间线设想

状态：最初的概念提案，已选定侧栏，并接入当前登录会话的终态事件。服务器历史和跨设备同步尚未实现。目前新增了独立的[开发 Demo](notifications-demo.md)，没有新增服务器端通知接口、持久化或 WebSocket 事件类型。任务 Demo 已选用列表与详情；时间线适合记录发生过的事件，任务页则保留当前状态和操作明细。

## 推荐入口与结构

顶部导航增加铃铛入口，以未读数量提醒；点击打开右侧通知面板，小屏使用全宽面板。日常查看在面板内完成，历史增长后再考虑完整通知页。默认按时间倒序，分为今天、昨天、更早；“全部 / 未读 / 需要处理”用于筛选。失败消息使用危险色，其他类型配合 SVG 图标、明确文字和时间，不能只靠颜色区分。

消息卡片建议包含：事件标题、资源名或批次摘要、AVID、发生时间、未读标记和相关入口。单资源事件可加小封面，批次消息使用摘要，点开后再展开失败项。封面缺失时用占位图，不阻塞通知阅读。

## 消息取舍

| 事件                      | 展示建议                       | 原因                           |
| ------------------------- | ------------------------------ | ------------------------------ |
| 下载完成、下载失败        | 一条结果消息，关联资源和任务   | 用户关心结果，失败需要定位原因 |
| 新增 / 刷新刮削完成或失败 | 区分动作，准确描述已完成的阶段 | 元数据保存与翻译完成是不同结果 |
| 批量添加结束              | 一条批次摘要，可展开失败项     | 避免几十条资源消息淹没时间线   |
| 下载进度、每个刮削阶段    | 留在任务详情，不产生独立通知   | 高频变化适合当前状态展示       |
| 外部搜索部分结果          | 留在当前搜索页                 | 结果陆续返回时保持阅读连续性   |

“需要处理”是待关注事件分类，不等于后台任务状态。失败后若任务已重试成功，原失败事件保留为历史，并关联后续结果；不要让旧通知误导用户认为任务当前仍失败。已读只代表看过，不代表问题已解决。

## 点击与提醒方式

点击“查看任务”定位到对应任务，重试、取消等操作放在任务详情中；通知面板不另造一套任务操作逻辑。“查看资源”定位到资源，资源已删除或任务历史失效时给出明确说明。普通完成消息只更新未读数量；失败是否弹出短提示、是否开启声音，应在后续讨论中确定，暂不默认打断用户。

## 若后续实施，需要先确定

- 通知属于当前浏览器、用户还是整个实例；是否需要跨设备历史与已读同步。
- 事件保存时长、历史分页、批次标识及被删除资源的处理方式。
- 哪些事件算“需要处理”，成功重试如何关联原事件，何时消除待处理提醒。
- 刮削及翻译的事件来源是否足以覆盖准确终态；本浏览器追踪任务不能代表完整历史。

届时优先由持久化事件承担历史；WebSocket 只提示有新事件，客户端按事件 ID 去重，并在重连后补读。现有即时 toast 和任务快照不能直接当作可靠通知历史。这些是实现前待确认的边界，不代表本轮已经建设通知能力。
