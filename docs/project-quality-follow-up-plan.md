## F1：统一资源删除和旧批量操作边界

范围：[资源视图](../django_backend/nassav/views.py)、[资源服务](../django_backend/nassav/resource_service.py)、现有持久化模块、相关测试与[接口文档](../django_backend/doc/interface.md)。此阶段不改变添加/刷新的异步新接口。

1. 先固定现有 API 合同和成功路径测试。定义一个共享的资源删除应用操作，由单条删除和批量 delete-all/delete 调用；文件定位、实际删除、数据库写入和删除结果由服务/适配器负责，视图只校验输入和映射响应。复用现有 ResourceService 或明确替换其删除入口，不并行保留多套相同删除逻辑。
2. 为 delete-video 复用同一文件/数据库状态边界，但保留其只删除视频、保留元数据的语义。缩略图、封面、视频和备份目录的处理规则在单条与批量全删中一致；返回的 deleted_files 只包含确认已删除的文件。
3. 明确不可原子的文件与数据库操作如何报告部分失败及如何重试。文件删除失败或数据库删除失败时不得回 200/成功；错误结果不能泄露本地路径或凭证，且保留足够信息供日志定位。重试应能完成未完成的删除，不误删其他 AVID；若需要改变既有失败响应，先更新接口文档和前端错误提示。
4. 将旧批量 add/refresh 中的数据库判定、固定等待和同步业务执行移至应用层，或在确认无调用方后按单独兼容计划退役。首轮保持旧 URL 和响应合同；固定等待是否仍需要，应以源站限流/重试证据决策，不能仅把 sleep 搬到另一个文件。
5. 用故障注入测试文件 unlink、备份目录删除、ORM 删除/更新失败，以及批量中单项失败后其他项的结果。覆盖仅有数据库行、仅有文件、重复请求、非法编号与并发同一 AVID；确认数据库和文件的最终状态与返回结果一致或明确标成可重试的部分失败。

**放行：**DeleteResourceView 与 ResourcesBatchView 的删除分支不直接执行文件删除或 ORM 删除/更新；旧批量 add/refresh 的流程编排与限流不留在视图中；单条与批量全删走同一实现，delete-video 的状态写入也有独立边界；故障注入不会得到虚假成功；原有成功响应、路径和前端流程回归通过；相关接口文档与[业务边界说明](../django_backend/doc/p5-domain-boundaries.md)同步更新。若旧同步 add/refresh 保留，文档明确兼容理由和后续去留，不把它误称为异步入口。

## F2：防止运行中的 PostgreSQL 栈被基础 Compose 误重建

范围：根 [基础 Compose](../compose.yaml)、[PostgreSQL 覆盖文件](../compose.postgres.yaml)、配置校验、环境样例、部署命令和必要的隔离测试。正式生产数据切换仍由数据库迁移计划负责。

1. 引入独立于所选 Compose 文件的“期望数据库模式”部署声明，并在迁移服务、API、三个 worker 和启用时的 Beat 连接数据库前与最终模式比对。对已经声明期望 PostgreSQL 的数据目录，误用基础文件必须明确失败，不允许静默连接 SQLite。具体持久化位置和恢复策略在实现前写清，不把测试目录标记带入生产。
2. 给正常 SQLite、正常 PostgreSQL、缺少覆盖文件、缺少 secret、目标库不可达分别建立配置和启动测试。失败测试使用隔离 Compose 项目、虚构凭证和独立数据目录；检查退出原因及没有创建意外的 SQLite 业务库。
3. 提供可重复使用的部署命令入口或检查脚本，始终携带正确的文件集合与项目名；在执行 up 前比较期望模式与运行容器标签，错误时不改动容器。展示脱敏的引擎、库名/schema 和文件标签。原生 docker compose 仍可被直接执行，因此应用侧的模式校验必须独立有效，并记录被绕过时可能发生的停机及恢复步骤。
4. 更新根 README 和[Compose 部署说明](../django_backend/doc/compose-deployment.md)：区分首次安装、开发库试运行和正式迁移；说明每次 up、ps、logs、exec、down 都应使用相同文件集合，并标出误用基础配置时的预期失败。

**放行：**两种正常模式均通过配置渲染和隔离启动；运行 PostgreSQL 模式后模拟误用基础配置时，受支持的部署入口在替换容器前拒绝，绕过入口的 migrate/API/worker 也在连接数据库前失败且不写 SQLite；原 PostgreSQL 和资源目录未改动。若绕过入口造成服务中断，恢复步骤已验证；所有后端服务的期望模式与实际模式一致，文档命令不输出 secret。不得在当前活动库上演练误切换。

## F3：目标环境验收

验收对象是计划部署的具体版本、域名/入口和服务集合；隔离测试成绩不代替本阶段。先检查目标环境的数据库、资源目录和回滚点，破坏性样本只能在隔离账号、测试记录或独立恢复库进行。

1. **访问和前端：**从另一台真实设备打开目标 HTTPS 页面，登录后分别完成只读和一次受控写入；验证 CSRF 拒绝、会话过期、匿名 API 401、非法 WebSocket Origin 拒绝、WSS 建连、断线重连和任务快照补查。记录浏览器、入口、时间与脱敏状态码；不得以 Vite 的模拟 Host 测试代替。
2. **任务链路：**在目标代理和 Byparr 配置下，用已确认可用的 MissAV/Jable 样本分别提交添加/刷新任务，记录入队、开始、终态与页面状态；用可合法测试的短媒体样本检查下载进度、文件大小和数据库状态。失败样本必须正确显示失败，不把队列接收当成业务成功。
3. **依赖与调度：**确认 API、三个 worker 和启用时的唯一 Beat 实际连接同一数据库与 Redis。若定时备份要求启用 Beat，观察至少一个完整备份周期；若不启用，明确写成“不适用”，不得声称自动备份通过。Ollama 若是启用的翻译依赖，验证一次实际翻译；未启用则列为未覆盖。
4. **备份恢复：**按[数据库迁移计划](../django_backend/doc/postgresql-migration-plan.md)在独立空 PostgreSQL 库执行备份与恢复，核对关键表、关联、序列和一条受控读写；资源目录单独核对。没有恢复验证时，不能将 PostgreSQL 备份能力标为已验收。
5. **观察与回滚：**记录至少一个实际任务高峰和所需备份周期内的连接错误、队列积压、失败率、磁盘/内存与代理错误。演练停止新写入、恢复原文件集合和镜像的步骤；真实切换后回滚的数据处理仍以数据库迁移计划为准。

**放行：**上述适用场景都有目标环境记录，失败项清零；不适用与未覆盖分开列出；备份可在独立库恢复；回滚步骤可执行。环境不具备时状态保持阻塞，不用本机自动化或容器健康检查替代。
