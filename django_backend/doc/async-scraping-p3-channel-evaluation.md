# P3 进度通道评估与 SSE 决策

日期：2026-09-26。分支：`chore/progress-channel-evaluation`，从 P2 分支创建。评估环境为本机 Django ASGI 直连、Redis 和现有 Celery 默认 worker；P4 的全栈 Compose 网关尚不存在。本记录不将本地直连结果当作目标代理环境验收。

## 发现与修复

连接时 `TaskConsumer.connect()` 同步调用 Celery `inspect` 获取下载队列状态。单次 WebSocket 握手约 3.0 秒；3 个客户端同时连接时，以前端配置的 5 秒超时测试，3 个均失败。`receive(get_queue_status)` 同样会阻塞事件循环。P3 将队列检查移到线程：连接先完成握手，初始快照异步发送；显式查询也异步执行。连接关闭时取消未完成的初始快照任务。未改变下载事件格式或其 Redis 进度快照。

后端全量测试 `uv run pytest tests/ -q`：260 项通过、13 项跳过；根目录 `pre-commit run -a` 为本阶段必需检查。

## SSE 决策

当前本地证据支持继续使用 **WebSocket + 签名状态查询**：修复同步队列检查后，握手与并发连接测试通过，丢失事件可由快照查询补齐；没有可复现的单向推送或代理问题需要 SSE。P3 不实施 SSE 原型，也不维护第二条实时通道。

P4 建成 Compose 网关后，仍须测代理升级头、目标环境连接成功率、断线恢复时间、并发连接数、实际下载进度间隔和反向代理空闲超时。若目标代理持续不能稳定升级 WebSocket，再单独开 SSE 原型分支并按计划验证鉴权、重连、心跳、缓冲与终态一致性。

## P4 网关补测

独立 Compose 网关下 3 路并发 WebSocket 握手均返回 101，耗时 25、41、42 ms，均收到 `queue_status`。刮削任务终态在 Redis AOF 重启后由签名状态查询恢复。短 HLS 样本完成下载，但执行过快，未产生可用于评估高频下载进度间隔的数据；真实长下载、代理断线恢复与目标环境连接率留在 P5。详见 [P4 验证记录](async-scraping-p4-validation.md)。
