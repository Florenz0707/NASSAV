## 抓取顺序

`browser_fetch_strategy` 独立决定请求顺序：

| 策略            | 顺序                 |
| --------------- | -------------------- |
| `direct_first`  | 先直连，失败后浏览器 |
| `browser_first` | 先浏览器，失败后直连 |
| `direct_only`   | 只直连               |

`BrowserFetch.session_reuse_enabled` 只决定完整会话复用、验证保存和刷新协调，不再将 `direct_first` 隐式转换为 `browser_first`。关闭时依旧采用传统 Cookie 直连方式；开启时复用 Cookie 与配套 UA，并校验出口、有效期和刷新版本。默认开关不变，不自动启用正式环境会话复用。

回归测试先复现关闭复用时错误先调浏览器的行为，修复后验证直连成功不调用浏览器、直连失败按序回退、关闭时不调用完整会话钩子。

## 逐页反馈

1. 沿用后台搜索任务，每个非空源页面完成后累计去重并按当前查询排序、分页。
2. 将阶段结果写入原任务 Redis 快照，保持 `running`，更新 `pages_completed` 与 `version`；`external_meta.partial=true`。
3. 通过既有登录 WebSocket 发布 `external_search_update`，仅含任务 ID、状态、版本和更新时间。
4. 前端收到新版本后立即携带签名 token 读取快照，展示卡片和页进度；每 1.5 秒轮询恢复断线或丢失通知。查询期间再收到通知，会立即追加一次查询，避免漏掉终态。
5. 成功终态将 `partial` 置为 false 后才写入完整结果缓存；后续页失败则保持 failed、保留最近阶段卡片并标记不完整，支持刷新重试。

演员与类别页均覆盖 MissAV 和 Jable。MissAV 保持原站顺序，Jable 随累计数据重新排序，因此阶段排序和总页数会变化。每次推送展示的是当前请求的应用分页窗口，用户请求较后的展示页时需要等待足够的累计数据。既有同步详情接口不执行推送，仍返回最终结果。

切源、换页和卸载会取消旧 HTTP 等待与事件订阅，后台任务继续；单调版本与原有请求标识共同阻止旧结果覆盖新结果。阶段数据不写入前端会话缓存，也不将已添加入库状态回退。终态保护阻止迟到源页恢复失败任务。

## 部署与验收

无需数据库迁移。更新 API、scrape worker 和前端后，使用演员/类别页分别选择 MissAV、Jable，并强制刷新以避开成功缓存。应先显示首批卡片、继续展示采集进度，随后完成；切源后旧任务不得覆盖当前页。若后续页失败，应保留已获取卡片并显示不完整提示，刷新允许重试。

正式环境要复用完整已验证会话，仍需明确开启 `BrowserFetch.session_reuse_enabled`，保证 Cookie 与配套 UA、代理出口有效；手工 Cookie 只保证传统直连会尝试使用，不能保证绕过站点挑战。
