# Byparr 请求链路的替代方案调研

日期：2026-09-30。范围：Jable、MissAV 详情页；依据是本仓库 P5 现场记录、Byparr **v3.0.4** 源码、上游项目文档及第一手案例。以下是研究和待验证假设，不是已放行的配置变更。

## 当前事实与证据边界

- [Jable P5](byparr-session-reuse-p5-record.md) 两窗口各 20 个有效详情页，Cookie+UA 暖直连有效率 50%/60%，P95 33.394/62.709 秒；[MissAV P5](byparr-session-reuse-p5-missav-record.md) 为 40%/50%，无 Cookie 直连 0/40，P95 24.228/61.264 秒。失败页通过 Byparr 回退得到有效内容。两站都未达到当前 95%、5 秒等放行门槛，全局会话复用仍关闭。这是 NASSAV 自己的实测，不能推广到其他站点、时段或出口。
- 两次现场检查中，直连与 Byparr 到出口查询服务的配对结果各为 3/3 相同 IP；这只能排除该时间和该查询目标上的简单出口不一致。它不证明目标站也看到完全相同的连接行为。[Cloudflare 的 clearance 文档](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/)说明 `cf_clearance` 绑定访客和设备，[JA4 文档](https://developers.cloudflare.com/bots/additional-configurations/ja3-ja4-fingerprint/)说明不同客户端会有可区分的连接特征；[Bot Score 文档](https://developers.cloudflare.com/bots/concepts/bot-score/)列出请求头、会话和浏览器信号。这些支持“同 IP、Cookie、UA 仍可能 403”的**机制假设**，尚不能证明 Jable/MissAV 的具体拦截规则。
- 本地 [MissAV.get_html()](../nassav/source/MissAV.py) 固定依序尝试 `/cn/{avid}-chinese-subtitle`、`/{avid}-chinese-subtitle`、`/cn/{avid}`；P5 探针从当时首页发现 46 个有效详情候选，包括 `/en/…` 和动态 `/dmN/en/…`。因此先核对真实目标 URL 的候选覆盖率。P5 的 20 页有效样本是从首页发现的，并不能证明上述三个生产候选也能取得同等成功率。这是本地观察，与 Byparr 上游能力无关。
- 2026-09-30 只读同容器、同一 Byparr 出口的两个单页对照：`FNS-258` 的前两条字幕候选分别花 30.329/28.491 秒且 `page_mismatch`，第三条 `/cn/fns-258` 花 19.854 秒并业务有效；首页 `/en/fns-258` 亦业务有效、23.337 秒。`MGOLD-064` 的前两条分别花 23.119/28.933 秒且 `page_mismatch`，第三条 `/cn/mgold-064` 花 32.915 秒并有效；首页 `/en/mgold-064` 有效、26.659 秒。前两个候选分别额外耗费约 **58.820/52.052 秒**。这只是两个番号与该时段的样本，无法推出全站候选命中率，必须扩大样本并检验是否真有字幕版本需求。

## Byparr v3.0.4 实际提供什么

- 固定部署镜像对应 v3.0.4。该版本 [`LinkRequest`](https://github.com/ThePhaseless/Byparr/blob/v3.0.4/src/models.py) 仅声明 GET、URL、`maxTimeout`、`blockMedia`、`returnOnlyCookies`，没有 `session` 字段或 `sessions.create`/`destroy` 路由。`cmd` 主要为 FlareSolverr 格式兼容；**不能把 FlareSolverr 的永久 session 参数直接发给当前 Byparr 并期待复用**。
- [`get_browser()`](https://github.com/ThePhaseless/Byparr/blob/v3.0.4/src/utils.py) 是每次 `/v1` 请求的依赖：用代理配置创建 `InvisiblePlaywright` 浏览器，再建 context/page，请求结束即退出依赖作用域。它支持环境级代理及 `X-Proxy-Server`、用户名、密码的逐请求覆盖；没有跨请求保存浏览器上下文的公开接口。持续保存 Cookie 到 NASSAV 数据库只保存 HTTP 状态，不会让 Byparr 在后续 `/v1` 调用中复用原浏览器。
- [`/v1` 实现](https://github.com/ThePhaseless/Byparr/blob/v3.0.4/src/endpoints.py) 使用 `page.goto()`，检测/处理挑战，再等 `networkidle`；`domcontentloaded` 后 `networkidle` 超时会继续。`blockMedia` 只拦截 image、media、font；其[默认值为 false](https://github.com/ThePhaseless/Byparr/blob/v3.0.4/src/consts.py)。`returnOnlyCookies` 会[省略 HTML](https://github.com/ThePhaseless/Byparr/blob/v3.0.4/src/content.py)，不适合详情解析。[Playwright 文档](https://playwright.dev/python/docs/api/class-page#page-goto)将 `networkidle` 标为不推荐的页面就绪判断，这给更精准的业务元素等待提供了实验方向；但源码不能证明它在本次 20–60 秒延迟中占多少。
- 当前 NASSAV 的 [ByparrPageClient](../nassav/page_fetching/browser.py) 已直接使用 `solution.response` HTML，再以 [PageFetchService](../nassav/page_fetching/service.py) 的同站、挑战和站点业务结构校验接纳。不能照搬“避免 Cookie 二次重放”的包装服务作为新优化：NASSAV 已经这样处理 Byparr 结果。[Byparr README](https://github.com/ThePhaseless/Byparr/blob/v3.0.4/README.md)也明确不保证挑战一定通过，并强调出口流量与 IP 的重要性。
- 在 Byparr/FlareSolverr 官方仓库及可检索的一手项目案例中，**未找到经 Jable 或 MissAV 详情业务结构验收、并给出同条件成功率与时延的会话复用成功案例**。上表 `byparr-proxy` 的实测对象是 1337x/Prowlarr；其他浏览器插件或采集项目的功能介绍也不能替代 NASSAV 的验收。

| 4      | **同一浏览器上下文中连续导航**              | Byparr 当前每请求新浏览器；复用 context 能共享 Cookie、浏览器网络状态及页面脚本环境，避免每页重启成本和 HTTP 客户端重放差异。[Playwright BrowserContext](https://playwright.dev/python/docs/api/class-browsercontext)支持上下文隔离与复用 Cookie，[FlareSolverr 官方 README](https://github.com/FlareSolverr/FlareSolverr/blob/master/README.md)的 `sessions.create` 则声称长驻浏览器可以免去每次启动与部分挑战。 | FlareSolverr 的浏览器栈与固定 Byparr v3.0.4 不同，永久 session 的文档承诺不等于这两个站可用。先用隔离的同类浏览器 PoC：同出口、单 context 顺序取 10 个不同详情，与逐页 Byparr 交错比较有效率、P50/P95、启动时间、内存与泄漏。限制最大页数/存活时间/并发并清理；若需要 fork Byparr，升级与维护成本较高。                                                                                                                              |

### 特别需要排除的捷径

- **只调大 timeout 或并发**：可减少客户端超时，但无法提升 403 的业务有效率；并发还可能增加浏览器内存与源站压力。[FlareSolverr README](https://github.com/FlareSolverr/FlareSolverr/blob/master/README.md)特别提醒浏览器内存和长驻 session 清理。只有先测到目标页可稳定成功且延迟来自等待，才考虑 timeout 调整。
- **仅更换 FlareSolverr**：其[官方 `sessions.create`/`request.get(session=...)`](https://github.com/FlareSolverr/FlareSolverr/blob/master/README.md)是实际功能，但成功案例与当前部署的浏览器实现不同。需锁定版本、隔离部署、同样出口和样本测试；不能把 Byparr 的 `/v1` 兼容性理解成两者会话能力一致。
- **仅更换 UA/复制 Cookie**：FlareSolverr 官方警告 clearance Cookie 须配套其 UA，[Cloudflare 文档](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/)进一步说明绑定访客/设备；P5 同出口的当前实现仍大量 403。UA 只是一项变量，不能作为放行依据。

## 建议实验次序与成功判据

1. 从 MissAV 生产目标番号抽取去标识化样本，确认真实链接发现与旧三个候选的业务有效率、每个详情平均浏览器请求数、累计时延。把路径失配单独修复和验证；Jable 保持对照。
2. 对两站采样规范 URL 重复率，再在只读/隔离环境试短 TTL 的**有效业务页**缓存与同键合并；分别报告冷页、暖缓存页、整体 API/worker 路径的 P50/P95 与 Byparr 调用数。若请求几乎都是不同页，此项收益有限。
3. 在固定 v3.0.4 的隔离实例上对 `blockMedia` 做交错 A/B，并分解浏览器启动、导航、挑战、等待和业务页面校验时间。仅当延迟瓶颈明确，才做持久 context 或业务元素等待 PoC；必要时以 FlareSolverr session 作并列对照，不替换正式服务。
4. 每种候选仍按 P5 门槛：两个独立时段、每窗口至少 20 个**业务有效**详情样本，直连/浏览器成功率、错误页误判、冷暖 P95、10 个不同页面的浏览器刷新数；随后才进入 API/worker、任务/下载/WebSocket 和 24 小时观察。记录代理、版本、路径样本构成，保留脱敏逐项结果。不因 200 或总共 40/40 回退有效而放行新链路。

目前最可检验的顺序是 **MissAV 路径覆盖率 → 重复请求比例 → Byparr 分段耗时 → 浏览器上下文复用**。它们解决不同原因，任何一项都没有本站的已验证提速承诺。
