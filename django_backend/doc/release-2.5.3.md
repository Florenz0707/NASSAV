## 升级步骤

当前迁移到0051；从v2.5.1/0036升级还涉及0037–0051，不只有版本字符串变更。已经迁移到0051的实例仍须检查代码/配置，但不重复运行业务导入。结构和归属区别见[数据库](database.md)与[切换手册](multi-user-cutover.md)。

| 范围           | 迁移      | 需要核查                                            |
| -------------- | --------- | --------------------------------------------------- |
| 资源与账号     | 0037–0039 | 旧资源只归指定原操作者，应用管理员角色显式引导      |
| 来源密钥       | 0040–0041 | 分类导入、未知Cookie隔离、原keyring及历史密钥备份   |
| 工作与版本     | 0042–0046 | 本人订阅、命令回执、版本指针和配额，不混跑旧writer  |
| 本人目录与历史 | 0047–0049 | 按本人版本投影；历史按池去重，单调时钟保护重看      |
| 资源回收       | 0050–0051 | 账本、宽限、占用及停止证明；结构存在不等于允许apply |

维护窗口停止所有旧写入者并备份DB/资产/keyring，先检查migrate计划，再应用结构、明确归属及导入。所有API/worker/Beat统一版本；回退须还原匹配的DB/文件/密钥，不能单独切旧代码。完整命令与预览规则见[切换手册](multi-user-cutover.md)，不要在聊天或日志输出秘密。

新模式默认开关均关闭；多用户依赖共享库和范围凭证，GC依赖共享库。本轮不修改操作者已选择的实际开关。启用前仍需核对本实例数据、角色、来源范围与相应验收，不能把隔离副本通过当成正式环境放行。

### Docker keyring 覆盖文件

宿主机HOST_FILE与容器FILE分别设置，始终复用可解密现有DB的原keyring；显式-f会覆盖COMPOSE_FILE，日常重建必须携带全部文件，例如：

```bash
docker compose -f compose.yaml -f compose.postgres.yaml -f compose.credentials.yaml up -d --build
```

SQLite去掉PostgreSQL文件；已有GPU等覆盖文件保留。API和三个worker统一只读挂载，不在镜像中复制密钥。/healthz正常仍可能缺少keyring，播放/刷新提交503时先查响应类别、挂载与只读来源绑定。见[部署说明](compose-deployment.md#独立来源-keyring-挂载)。
