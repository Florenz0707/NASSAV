# Byparr 第四步：候选方案两窗口验收

日期：2026-10-01。对应[替代方案调研的执行次序第 4 步](byparr-alternative-approaches-research.md)，不是优先级表中的浏览器 context 连续导航实验。范围是第三步留下的 Jable 业务就绪等待候选；blockMedia 已因尾部收益不足停止，MissAV 的主要耗时为导航，不把 Jable 等待结论推广到该站。

## 方法和实现

- 固定 Byparr v3.0.4 镜像 digest 与第三步一致。默认/候选使用相同 Docker 网络、512 MiB 共享内存、host-gateway 和 API 配置代理路线，无宿主端口。每次请求仍新建浏览器，不复用 context；版本与代理配置一致不能证明目标站所见的 IP 或连接特征永久一致。
- 候选新增隔离 `business_bounded` 模式，原 navigation、挑战求解、DOM 和总请求预算保持原样。最终等待阶段同时启动原 networkidle 与最多 2 秒的业务检查；检查只读取 HTML，同站点且请求番号、播放地址和封面完整才提前返回。检查未通过时继续已经运行的原等待，不增加一个串行等待周期，也不把提供方 200 当作业务成功。
- [有界等待实现](../scripts/byparr/bounded_wait.py) 为两个等待任务提供完成/取消清理。业务提前完成的 networkidle 计时代表取消前的运行时间，不能视为页面真的达到 networkidle。返回时仍取新的 HTML 快照，探针通过真实 Jable.parse_html、番号、标题、播放地址和封面再次验证。
- 冷 A/B：每窗口 20 个不同详情，奇偶交错默认/候选；第二窗口重用清单并反转顺序。每窗口两臂都请求不存在详情，失败和慢请求保留在 P95 中。
- 暖链路：各窗口重新发现详情及获取浏览器 Cookie+UA；种子必须在 3 秒内通过同页直连验证，之后同会话依次请求至少 20 个不同页，失败时通过隔离候选回退。没有 HTML 缓存命中。种子发现/验证请求与详情请求分开记录；前 10 页浏览器调用包括详情回退，不以“刷新尝试合并”掩盖每页仍需浏览器的事实。
- 正式配置、Cookie 表、资源、Redis、任务队列均不写入。会话只存在探针进程内存，不记录 Cookie、UA、代理凭据、出口 IP、页面或完整 URL。

## 放行判据

按原 P5 门槛逐窗口评估：至少 20 个不同有效详情，暖直连率至少 95%，错误页误接纳为零，暖 P95 小于 5 秒且小于同环境默认 Byparr 单页中位数的 25%，前 10 个不同详情至多一次浏览器刷新/回退。所有暖请求作为直连率分母，失败也纳入 P95；不会只挑有效或快请求。

[门槛评估脚本](../scripts/assess_byparr_acceptance.py) 通过只表示预筛可继续，不等于正式放行。任一门槛未通过则保持原链路；API/worker、任务/下载/WebSocket 与 24 小时观察仅在预筛通过后进入。

## 两窗口结果：预筛通过

原始数据与最终门槛输出见 [170 条脱敏证据](byparr-candidate-acceptance-evidence.jsonl)，保留首次 API 失败及随后复现，不删除失败样本。

| 窗口（北京时间）              | 默认/候选冷页有效 | 默认冷 P50/P95   | 候选冷 P50/P95   | 配对节省中位数         | 暖直连有效 | 暖 P95   | 前 10 页浏览器调用 |
| ----------------------------- | ----------------- | ---------------- | ---------------- | ---------------------- | ---------- | -------- | ------------------ |
| W1 冷 13:30–13:41；暖至 13:42 | 20/20、20/20      | 17.836/23.142 秒 | 10.226/16.314 秒 | 7.304 秒（19/20 更快） | 20/20      | 0.672 秒 | 0                  |
| W2 冷 13:43–13:53；暖至 13:55 | 20/20、20/20      | 17.408/25.124 秒 | 10.038/14.333 秒 | 7.026 秒（20/20 更快） | 20/20      | 0.673 秒 | 0                  |

冷窗口重用完全相同的 20 个番号。暖窗口重新从列表发现，排除浏览器种子页，因此其 20 页与冷清单存在一个番号的差异；两份清单及种子请求均保留在证据中。每窗口均重新获取并完成同页直连验证，未共享上一窗口 Cookie，也未命中 HTML 缓存。默认 Byparr 中位数的 25% 分别为 4.459/4.352 秒，暖 P95 同时低于该值和 5 秒。

不存在页的默认/候选耗时：W1 为 11.636/11.555 秒，W2 为 17.153/12.177 秒，4 次均 page_mismatch，零误接纳。候选走原等待回退，分别约 1.368/1.550 秒结束，没有第三步初始 PoC 的整段预算耗尽。单窗口的微小耗时差异不能证明所有不存在页都同速；慢读取、预算耗尽和任务取消另外有离线测试。

冷对照完成后，联调实例加入只读浏览器请求计数，并补充原等待与业务检查同时结束时的异常传播防护；有界模式仅对已测的 Jable 详情生效，其他站点/列表维持原等待。成功页面的等待逻辑不变，最终安全防护经离线契约及联调检查；最终实现的发布验收仍需在修复以下入口后重做，不把前述初始候选两窗口当作正式发布证书。

## API/worker：整体 NO-GO

使用正式后端同一镜像，但数据库为新建 PostgreSQL 16 空库，Redis 为独立实例，资源仅存容器 `/tmp/acceptance-resource`。所有迁移成功，7 个核心页面/会话文件与工作树 SHA-256 一致。真实 Celery worker 分别使用 `-c 1` 和 `-c 2`；API 用 Django/DRF 客户端调用实际路由和视图，WebSocket 通过实际 ASGI consumer 和独立 Redis 接收 worker 事件，不将进程内测试客户端等同完整反向代理验收。

| 检查                                | 结果                                                                         |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| 手动 Cookie POST、DELETE、GET       | POST/DELETE/GET 均 200；旧请求无 UA 不保留历史配套字段                       |
| Jable 自动 Cookie POST              | 500，未得到配套会话；重复复现仍失败                                          |
| `-c 1` 详情刷新任务                 | 202 提交，任务 succeeded；收到 1 个成功 WebSocket 终态；1 次浏览器访问       |
| `-c 2` + 同步刷新 API               | 10/10 任务 succeeded，10 个成功 WebSocket 终态，同步 API 200；0 次浏览器调用 |
| 跨进程共享会话                      | 独立 PostgreSQL 中 Cookie、配套 UA 和路线标识均存在；混合调用使用已保存会话  |
| 媒体下载、配置回滚演练、24 小时观察 | 未进入；自动 Cookie 入口未通过，正式链路不切换                               |

阻塞有明确复现：自动入口的 1 次受控请求中，HTTP 首页返回 403、Cookie 数为 0、Byparr 调用数为 0，API 返回 500。Jable 继承 [SourceBase.set_cookie_auto](../nassav/source/SourceBase.py)，其中仍是旧的直连 Cookie 抓取；[SourceManager.auto_source_cookie](../nassav/source/SourceManager.py) 虽有刷新协调，但没有将该入口改为浏览器获取 Cookie+UA、同页直连验证后保存。详情任务能获取和共享浏览器会话，并不证明自动管理入口可用。该入口沿用既有实现，仍属于必须满足的 P4/P5 管理入口门槛。

**最终 NO-GO：两窗口预筛通过，但自动 Cookie 管理入口未通过。** 下一项修复应让 Jable 自动获取复用现有浏览器会话获取、校验、版本检查和刷新租约，保留手动覆盖/清除语义，拒绝未经验证的 HTML 或 Cookie；完成后重做管理入口及最终候选两窗口，再继续媒体下载、回滚和至少 24 小时观察。本次交付包括实验工具与验收证据；入口修复列为下一开发项。正式复用开关和页面策略维持原状。

## 离线验证与收尾

完整后端回归为 418 passed、13 skipped；最终等待、门槛、探针及数据库相关测试另运行，30 passed。环境中 PostgreSQL 失败端口会返回“server closed the connection unexpectedly”，旧测试只认拒绝/超时字样导致一次失败；现断言实际选用 PostgreSQL、抛出 OperationalError 且无 SQLite 回退文件，契约保持，完整回归重跑通过。六个临时实验容器（含独立数据库/队列）、API 容器的临时探针目录、宿主私有配置/凭据及结果临时文件均已清理；保留脱敏证据和可复现实验工具。`pre-commit run -a` 全部检查通过。
